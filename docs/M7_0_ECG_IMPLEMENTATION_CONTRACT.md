# M7-0 — ECG Implementation Contract (DESIGN ONLY, NOT IMPLEMENTED)

Draft technical interface for whichever model M6's human checkpoint
selects. Nothing below is implemented. No file listed here has been
created or modified as production code. This refines
`docs/M7_ECG_IMPLEMENTATION_PLAN.md`'s stage descriptions into an
explicit input/process/output contract, per this milestone's Phase 12
instruction.

## INPUT

| Item | Source | Status |
|---|---|---|
| Patient record | Existing `Patient` object (`schemas/patient_schema.py`), already generated by `integration/build_patient.py` | EXISTS |
| ECG conditioning representation | `ECGRecord.superclasses` (existing, 5-class) **and/or** a new 71-dim SCP vector (per `docs/M7_0_CONDITIONING_AUDIT.md` §5 — recoverable from local data, NOT YET EXTRACTED) | PARTIALLY EXISTS |
| Random seed | Existing per-patient `(sequence, seed)` scheme (`tests/test_stage2_foundation.py`'s reproducibility contract) | EXISTS, not yet extended to a generation seed |
| Model configuration | Model name/version, checkpoint identity, device, precision (fp32/fp16) | DOES NOT EXIST YET |

## PROCESS

1. **Conditioning construction** — build the model-specific label vector
   from the patient's already-selected source `ecg_id` (via the existing
   `pick_ecg_id()`/`load_ptbxl_record()` selection — no new selection
   logic). Exact vector width/order per
   `docs/M7_0_CONDITIONING_AUDIT.md` §6 (unresolved: precise index
   order without checkpoint confirmation).
2. **Model inference** — load the selected model's pretrained checkpoint
   once per process (matching the existing `functools.lru_cache`
   pattern already used for PTB-XL CSV/label-map loading,
   `ingestion/ptbxl_source.py`), run inference for the conditioning
   vector + a generation seed, producing a raw waveform tensor in the
   model's native shape/order.
3. **Tensor conversion** — deterministic transpose + lead-order
   permutation (`docs/M6_ECG_MODEL_SELECTION.md` §7, Option B) into
   `[1000, 12]`, standard clinical lead order. Pure function, no
   randomness.
4. **Amplitude/de-normalization** — **NEW OPEN ITEM this session**
   (`docs/M7_0_ECG_READINESS_REPORT.md` §6): whether the model's raw
   output is in physical mV units or a standardized (mean-0/std-1)
   space is UNRESOLVED — `train.py` shows no normalization applied to
   the loaded training array, but that array's own provenance/units are
   not independently confirmed. **This step may be a no-op or may
   require a documented de-normalization constant — not decidable until
   M7-3 produces a real sample to compare against real PTB-XL amplitude
   ranges.**
5. **Validation** — run `docs/M6_ECG_VALIDATION_PLAN.md`'s HARD FAILURE
   tier (shape, rate, lead order, NaN/Inf, amplitude bounds) before
   accepting the waveform.

## OUTPUT

| Item | Design |
|---|---|
| Canonical waveform | `[1000, 12]` float array, standard clinical lead order, physical-unit amplitude (pending §Process-4 resolution) |
| Metadata linkage | References the same `ecg_id` already on `ECGRecord` — does NOT introduce a second, competing identifier for the *source* record |
| Provenance | Model name, model version/commit, checkpoint identity (hash or filename), generation seed, conversion-step version — additive fields, not yet added to `schemas/patient_schema.py` |
| `ECGRecord.signal_available` | Flips from the current universal `False` to `True` only for records with a validated attached waveform — reuses the existing field, no new flag needed |

## Deterministic reproducibility

Must extend, not replace, the existing per-patient `(sequence, seed)`
determinism. The generation seed fed to the model must incorporate the
synthetic `patient_id`/sequence — **not only the shared source
`ecg_id`** — otherwise two patients whose independent sampling happens
to select the same source `ecg_id` (already measured: 17,386 unique
ids across 100,000 patients, max reuse 17×, `docs/M5_100K_DATASET_REPORT.md`)
would receive a byte-identical generated waveform, tripping
`docs/M6_ECG_VALIDATION_PLAN.md` item #12's HARD FAILURE duplicate
check. Not implemented; the rule is stated here so M7-3/M7-6 don't
reintroduce this bug.

## Patient-ID ↔ ECG linkage

Unchanged from today: one synthetic `patient_id` maps to exactly one
source `ecg_id` (already selected deterministically by
`pick_ecg_id()`), which in turn maps to exactly one generated waveform
once Stage 4 exists. No many-to-many mapping is introduced by this
contract.

## ECG ID policy

- **Source PTB-XL `ecg_id`** — remains exactly what D003 already
  established: metadata provenance, identifying which real record's
  *labels* (not waveform) informed conditioning. **May appear in
  synthetic output, unchanged from today** — it already does, as
  metadata, and this has never been treated as exposing real waveform
  content since no real waveform has ever been attached.
- **A synthetic-waveform identifier is NOT yet defined.** Recommendation
  (not a decision): a separate field (e.g. a UUID or a deterministic
  hash of `patient_id` + model + seed) so a reviewer can never confuse
  "which real PTB-XL record's labels were used" with "which specific
  generated array this is" — these are different facts once a real
  waveform exists, whereas today only the first fact exists at all.

## Storage format — options presented, not decided

| Option | Pros | Cons |
|---|---|---|
| Inline in patient JSON (nested array) | No new file format; simplest to read | ~48KB/patient (float32) added to every JSON — a ~14× increase over M5's measured 3,551 bytes/patient metadata baseline; awkward for tools that parse JSON without needing the waveform |
| External `.npy`/`.h5`, referenced by path/id | Matches existing precedent for large PTB-XL binaries (excluded from git via `.gitignore`); keeps patient JSON small and diff-friendly | Two-file-per-patient bookkeeping; referential integrity (a JSON pointing at a missing/renamed array file) becomes a new failure mode requiring its own validation check |

**Not decided here** — flagged as an M7-5 human checkpoint per
`docs/M7_ECG_IMPLEMENTATION_PLAN.md`.

## Dtype recommendation

**float32 for generation and validation** (matches the model's own
apparent training dtype — no explicit fp16 training path found in the
fetched code), with an **optional float16 storage-only cast** evaluated
at M7-8 scale-readiness time if storage becomes a real constraint
(`docs/M6_ECG_MODEL_SELECTION.md` §10's float16 column — 2.4GB vs 4.8GB
at 100K). Not decided; a recommendation for M7-5/M7-8 to revisit with
real numbers.

## Compression recommendation

**None at this stage.** Per `docs/M6_ECG_MODEL_SELECTION.md` §10's
explicit instruction not to introduce compression without evaluation —
carried forward unchanged. If storage becomes a real constraint at
M7-8, evaluate then, with real measured sizes, not before.
