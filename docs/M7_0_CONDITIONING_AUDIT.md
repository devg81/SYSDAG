# M7-0 — Conditioning Audit: the 44-vs-71 SCP-Code Question

**Research only. No schema/code changed. No scp_codes field added to
`schemas/patient_schema.py`.** This narrowly investigates the single
open question `docs/M6_ECG_MODEL_SELECTION.md` §2/§11-2 flagged as
unresolved. Everything below is sourced from direct fetches of
SSSD-ECG's actual repository files (raw GitHub, this session), not
summaries of summaries, and from this project's own local PTB-XL CSVs.

## 1. Where "44" comes from

Confirmed directly from `syngen/SynGen/SynGen/dataset/scp_statements.csv`
(this project's own local file): **71 total rows**, of which **exactly
44** have `diagnostic == 1`. Confirmed directly from SSSD-ECG's
`src/ptb_xl/clinical_ts/ecg_utils.py`, function `prepare_data_ptb_xl()`:

```python
ptb_xl_label_diag = ptb_xl_label_df[ptb_xl_label_df.diagnostic > 0]
df_ptb_xl["label_diag"] = df_ptb_xl.scp_codes.apply(
    lambda x: [y for y in x.keys() if y in ptb_xl_label_diag.index]
)
```

This is a real code path in SSSD-ECG's own repository. It genuinely
filters to the 44 diagnostic-flagged statements. **This part of the
prior session's finding was correct — the discrepancy is not that "44"
was wrong, it's that `label_diag` is very likely NOT the array the
released diffusion checkpoint actually trains on** (see §3).

## 2. Where "71" comes from — now more precisely located

`src/sssd/config/config_SSSD_ECG.json`'s `wavenet_config.label_embed_classes:
71` is a **hard architectural constraint**, not a loosely-chosen number.
Fetching `src/sssd/models/SSSD_ECG.py` directly shows the label input is
consumed as:

```python
nn.Embedding(label_embed_classes, label_embed_dim)   # a [71, 128] weight matrix
...
label_embed = label @ self.embedding.weight            # matmul, not index lookup
```

A matrix multiply `label @ embedding.weight` requires `label`'s last
dimension to equal `embedding.weight`'s first dimension **exactly** —
71. This is not a configuration default that could silently be ignored;
if the actual training label array's width were 44, this matmul would
raise a shape-mismatch error during training. **This is strong,
code-level proof that whatever array the released checkpoint was
actually trained on has exactly 71 columns — not 44.**

## 3. Reconciling the two facts — `label_all`, not `label_diag`, is the likely candidate

`prepare_data_ptb_xl()` does not build only `label_diag`. Direct
inspection of the full function shows it builds **six** label arrays via
`map_and_filter_labels()`:

```python
ptb_xl_label_diag   = ptb_xl_label_df[ptb_xl_label_df.diagnostic > 0]   # 44 rows
ptb_xl_label_form   = ptb_xl_label_df[ptb_xl_label_df.form > 0]
ptb_xl_label_rhythm = ptb_xl_label_df[ptb_xl_label_df.rhythm > 0]
```

...producing `label_diag`, `label_form`, `label_rhythm`,
`label_diag_subclass`, `label_diag_superclass`, and — critically —
**`label_all`**, described in the fetched code summary as using **all
codes, unfiltered by the diagnostic/form/rhythm split**. A 71-row
scp_statements table with no filter applied is, by construction, the
one candidate among these six whose vocabulary size can equal exactly
71 (assuming every one of the 71 codes appears at least once — plausible
across ~21,837 records, though not independently confirmed by count).

**The preprocessing notebook's own `ptb_xl_label = "label_diag"`
variable (which the prior session's audit read) governs a *different*
downstream use in that notebook — not necessarily the array
`train.py` actually loads.** Confirmed directly: `train.py` loads
`ptbxl_train_data.npy` (signal) and a `labels_ptbxl` array — **not**
generated by the fetched `ecg_data_preprocessing.ipynb` (that notebook
contains **no `np.save()` call at all**), so the exact script/cell that
produced the released `ptbxl_train_labels.npy` file is not present in
the fetched files, and this project cannot inspect it directly.

## 4. Verdict on the 44-vs-71 question

**RESOLVED WITH HIGH CONFIDENCE, NOT DEFINITIVELY PROVEN:**

- The model architecture's conditioning input is unambiguously
  71-dimensional (§2 — a hard shape constraint, not an inference).
- The most parsimonious explanation, given the repo's own code builds a
  `label_all` (unfiltered, all-71) array as one of six precomputed
  options, is that **`label_all` — not `label_diag` — is what the
  released checkpoint actually trains on.**
- This **cannot be fully proven** without one of: (a) the actual
  `ptbxl_train_labels.npy` file's shape, (b) the checkpoint's own
  `embedding.weight` tensor shape (`[71, 128]` would confirm it,
  anything else would falsify this conclusion), or (c) the exact script
  that produced that npy file, none of which this session could access
  (checkpoint is license-blocked; the producing script is not in the
  fetched repository tree).
- **What is definitively FALSE:** the notion that the checkpoint was
  trained on a 44-length diagnostic-only vector. That would fail the
  matmul in §2 outright. If `label_diag` (44) is used anywhere in this
  codebase, it is for a different purpose (e.g. the paper's own
  classifier-based evaluation, not diffusion-model conditioning) — not
  yet located in this session's scope.

## 5. Can this project's local PTB-XL data supply a `label_all`-equivalent vector?

**Yes, essentially directly.** `syngen/SynGen/SynGen/dataset/
scp_statements.csv` already has all 71 SCP statement rows (no filtering
applied), and `ptbxl_database.csv`'s `scp_codes` column already carries
the full per-record confidence-weighted dict over these codes (e.g.
`ecg_id=1` → `{'NORM': 100.0, 'LVOLT': 0.0, 'SR': 0.0}`). Building a
71-length multi-hot (or confidence-weighted) vector per `ecg_id`, in
`scp_statements.csv`'s own row order, is a direct, deterministic
transformation of data this project already has — **not** a new
dataset, and not a redesign. This upgrades §3's M6 finding
("PARTIAL, leaning INCOMPATIBLE-AS-IS") to **"the raw vector is
recoverable in full from local data — what remains unverified is only
the exact column *order* the checkpoint expects."**

## 6. What remains genuinely unresolved

1. **Exact index order.** `scp_statements.csv`'s row order in this
   project's local file is not guaranteed to match whatever
   `lbl_itos_ptb_xl["label_all"]`-equivalent ordering SSSD-ECG's own
   pipeline produced (likely `sorted(unique codes)` per
   `map_and_filter_labels()`'s described behavior — "creates numeric
   mappings via sorted unique label extraction" — which would in fact
   make it reconstructible: alphabetically sorting this project's own
   71 SCP code strings should reproduce the same order IF SSSD-ECG's
   vocabulary construction really is a plain sorted-unique over all 71
   codes with no `min_cnt` filtering removing any of them. **Plausible,
   not confirmed** — a genuine remaining risk if even one code got
   filtered out by an undiscovered `min_cnt` step, shifting every
   subsequent index.
2. **Whether `label_all` is confidence-weighted (SSSD-ECG's raw
   `scp_codes` value, e.g. 100.0/80.0) or strictly binarized (0/1) at
   the point it becomes a training array** — not established from the
   fetched code; `map_and_filter_labels`'s description ("numeric
   mappings via sorted unique label extraction") suggests categorical/
   binarized handling but this is inferred, not quoted verbatim from a
   binarization line.
3. **No independent confirmation via the checkpoint itself** — the
   single fact that would fully settle this (the embedding weight
   matrix's shape and, ideally, a shipped vocabulary/order file) remains
   behind the same license-blocked Figshare link as
   `docs/M6_ECG_MODEL_SELECTION.md` §4.

## 7. Deterministic mapping assessment (per this milestone's instruction)

- **A deterministic 71→44 reduction** (all-71 vector → diagnostic-only
  subset) is straightforward and lossless *as a projection* (just drop
  the 27 non-diagnostic columns) — but is the wrong direction for using
  the pretrained checkpoint, which needs the full 71, not a reduced 44.
- **A deterministic 44→71 expansion** (starting only from diagnostic
  codes and padding the remaining 27 form/rhythm slots) would
  **introduce false information** — it would claim "no form/rhythm
  abnormality present" for records where this project simply never
  looked, not where the source data confirms absence. **Not
  recommended** — this project's own local `scp_codes` column already
  makes this unnecessary anyway (§5): the full 71-dim vector, including
  real form/rhythm values, is directly available without needing to pad
  or guess.
- **No mapping is implemented in this document.** This is analysis, not
  code.
